# VisionLife Architecture

This document explains how the current VisionLife system works in plain language.

It is written for a human reader first, not as API reference.

## 1. What VisionLife Is

VisionLife is a local Python system that:

1. watches or receives media files
2. prepares them for analysis
3. analyzes them with local and cloud logic
4. stores a history of what happened
5. protects sensitive documents
6. writes human-readable dashboard notes
7. shows those notes in a local command-desk dashboard

The dashboard is not the source of ingestion truth.
The dashboard is the main reading and interaction surface for the analyzed outputs.

## 2. High-Level Runtime Flow

The full media pipeline looks like this:

1. A file appears in an inbox.
2. The watcher or batch runner sees the file.
3. The file is deduplicated using a content hash.
4. The file is prepared:
   - images may be resized
   - videos may be reduced to a key frame
   - HEIC/HEIF may be converted
   - PDFs may be rendered for analysis
5. A local fast-sort gate may discard obvious junk.
6. OpenAI vision analysis runs.
7. The result may be enriched with web-assisted research.
8. Sensitive items are diverted into the encrypted `ID` vault.
9. Non-sensitive items are written as Markdown notes.
10. The dashboard reads those notes and local UI state.

## 3. Main Project Areas

### Ingestion and Orchestration

- [watcher.py](./visionlife/watcher.py)
  Testing-oriented watcher entrypoint. Watches the Desktop shortcut / test inbox.

- [main.py](./visionlife/main.py)
  Shared runtime/bootstrap logic used by the watcher and processing pipeline.

- [pipeline/orchestrator.py](./visionlife/pipeline/orchestrator.py)
  Coordinates the explicit processing stages:
  stabilize -> dedupe -> prepare -> fast sort -> analyze -> publish

### Analysis and Media Preparation

- [vision.py](./visionlife/vision.py)
  OpenAI-facing analysis layer. Builds prompts, handles retries, and returns structured results.

- [utils.py](./visionlife/utils.py)
  Local file/media preparation logic.

- [fast_sort.py](./visionlife/fast_sort.py)
  Local Apple Silicon fast-sort model path.

### State and Storage

- [db.py](./visionlife/db.py)
  SQLite history tracking for dedupe and processing state.

- [records.py](./visionlife/records.py)
  Canonical typed record layer for analysis results.

### Service Layer

- [services/calendar_service.py](./visionlife/services/calendar_service.py)
  Event/ticket/reservation inference and Google Calendar prompt shaping.

- [services/dashboard_service.py](./visionlife/services/dashboard_service.py)
  Converts processed results into dashboard Markdown notes.

- [services/sensitivity_service.py](./visionlife/services/sensitivity_service.py)
  Detects sensitive PII/PDD-style artifacts and moves them into the encrypted `ID` vault.

### Front End / Presentation

- [results_app.py](./visionlife/results_app.py)
  Compatibility launcher plus current rendering/controller logic.
  This is still larger than it should be, but it is being broken apart.

- [presentation/web/app.py](./visionlife/presentation/web/app.py)
  Local HTTP entrypoint for the dashboard.

- [presentation/web/view_models.py](./visionlife/presentation/web/view_models.py)
  Typed front-end models for notes, tracker rows, groups, tasks, and time slices.

- [presentation/web/view_builders.py](./visionlife/presentation/web/view_builders.py)
  Small context builders that shape data before templates receive it.

- [presentation/web/templates](./visionlife/presentation/web/templates)
  Server-rendered HTML templates for the dashboard shell and components.

- [presentation/web/static/dashboard.css](./visionlife/presentation/web/static/dashboard.css)
  Visual styling for the command desk.

- [presentation/web/static/dashboard.js](./visionlife/presentation/web/static/dashboard.js)
  Client-side interaction layer for editing, approvals, to-dos, and calendar actions.

## 4. Dashboard Data Sources

The dashboard currently combines three sources of truth:

1. Markdown notes
   Generated by the ingestion pipeline.
   These are the main analyzed artifacts the user reads.

2. Dashboard config
   Stored in:
   [dashboard_config.json](./visionlife/app_assets/dashboard_config.json)

   This controls:
   - row groups
   - row labels
   - row capacities
   - header phrases
   - background imagery

3. Dashboard state
   Stored in:
   [dashboard_state.json](./visionlife/app_assets/dashboard_state.json)

   This stores:
   - cell status colors
   - cell notes
   - artifact approval/reassignment state
   - to-do items

This means the dashboard is currently a blend of pipeline output plus local UI state.

## 5. How the Command Desk Home Works

The command desk home has these regions:

### Header

Contains:
- inscription
- affirmation
- rotating phrase

These are editable and saved back into dashboard config.

### Temporal Rail

The timeline now uses a scale-aware `TimeSlice` model.

The current display logic is:
- `Today` = focus slice
- `Yesterday` and `Tomorrow` = near slices
- nearby days = compressed slices
- `Last Week` and `Next Week` = week-band slices

Purpose:
- near time stays readable
- farther time becomes signal
- color still tells the story as time compresses

### Tracker Grid

Each row represents a life category.
Each visible time slice becomes a column or band.

Each cell can hold:
- one main status color
- artifact chips
- calendar prompt icon
- a short note preview for focus-scale cells

### Right Drawer

The drawer changes by selected row:

- standard row:
  review artifacts, approve/reassign them, save a cell note, set color state

- `To-Do list` row:
  becomes a capture-and-routing mini-panel

### Weekly Cards

Currently shown automatically for:
- `Spend one hour a day experimenting with AI`
- `Relationship`

Purpose:
- not streaks
- weekly interpretation and pattern reading

## 6. How the To-Do List Works

The `To-Do list` row is not just another status row.
It acts like a capture inbox for lightweight planning.

Each to-do item stores:
- text
- type
- estimated time preset
- suggested row
- suggested day
- approved flag
- done flag

The initial supported types are:
- admin
- work
- health
- relationship
- home
- event
- follow-up
- idea

The initial supported time presets are:
- 15m
- 30m
- 1h
- 2h
- 4h

### Scheduling Logic

When you create a to-do:

1. It is captured on the selected day.
2. Its type is used to infer a target tracker row.
3. Its estimated time is compared against that row’s per-day capacity.
4. The system proposes the next near-future day that still has room.
5. The item remains visible:
   - in the `To-Do list` drawer for the source day
   - as a provisional task chip in the suggested future row/date cell

This is meant to support planning without immediately losing the original capture context.

## 7. How Artifact Approval Works

VisionLife can suggest that an artifact belongs in a certain row.

That suggestion is not final.

Artifact assignment state currently supports:
- approved
- highlighted
- archived
- save_for_later
- reassigned row

So an artifact can exist as:
- provisional
- approved
- re-routed
- archived out of the main working surface

## 8. How the Front-End Layers Are Divided

This is the current intended separation:

### Templates
Templates control HTML structure.

Examples:
- page shell
- drawer shell
- tracker shell
- repeated item markup

### CSS
CSS controls:
- appearance
- spacing
- temporal density
- color treatment
- background art

### JS
JS controls:
- saving config edits
- updating cell status
- saving cell notes
- reassigning artifacts
- creating/updating to-dos
- opening calendar prompts

### View Builders
View builders should shape the data passed into templates.

This is still partial.
Some context shaping still lives in `results_app.py`.

### results_app.py
Currently still acts as:
- controller
- router
- part renderer
- part view assembler

That file is being gradually reduced.

## 9. What Still Needs Refactoring

The front end is cleaner than before, but not finished.

The biggest remaining cleanup items are:

1. Move more drawer and grid context shaping into [view_builders.py](./visionlife/presentation/web/view_builders.py)
2. Extract more repeated HTML helpers into templates
3. Move note-detail rendering into templates
4. Shrink [results_app.py](./visionlife/results_app.py) into a controller layer instead of a hybrid controller/view
5. Move toward a single canonical dashboard payload rather than mixing note parsing and local state derivation ad hoc

## 10. Practical Rule of Thumb

If you want to change:

- layout structure:
  start in templates

- visual styling:
  start in CSS

- interactions:
  start in JS

- what data appears in a component:
  check view builders and renderer logic

- scheduling, assignment, or interpretation rules:
  check Python logic, not templates

## 11. Current Design Intent

The command desk is designed to feel like:
- a daily focus surface
- a tracker first
- a private working archive
- a place where evidence accumulates
- a system where the color history still tells the truth even after detail compresses

The main visual idea is:
- today is large enough to work in
- near time is readable
- far time becomes pattern
- the story of the row survives even when the detail disappears
